# ARCHITECTURE — почему именно так

Здесь объяснено, почему принято каждое неочевидное решение. Если что-то в рецептах кажется странным — ответ, скорее всего, тут.

---

## Почему Windows, а не Linux

**Короткий ответ:** Claude Code Desktop — GUI-приложение.

Та же конфигурация на Linux стоит в два-три раза меньше, грузится быстрее и не требует RDP. Если тебя устраивает CLI-версия Claude Code, Linux-сервер будет лучше по всем параметрам — и это честно самая серьёзная претензия к схеме.

Windows выбран ровно по одной причине: нужен десктопный интерфейс. Если это не твой случай — не повторяй эту часть.

---

## Зачем отдельный рабочий пользователь

**Изоляция конфигов Claude Code и чистая история.**

Под `Administrator` со временем накапливается огромный объём: сессии, проекты, бэкапы. Миграция на новую машину становится операцией «всё или ничего». Отдельная учётка даёт чистый старт, не трогая того, что уже сделано под админом.

**Чего здесь НЕТ:** изначально у меня была теория, что админские права ломают свободный режим разрешений Claude Code. **Она оказалась неверной.** Реальная причина сброса режима — баг в самом Claude Code (см. ниже). Пишу об этом, потому что сам потратил на эту гипотезу время.

### Почему рабочий пользователь всё равно администратор

Proxifier с перехватом чужого трафика требует elevation. Без прав администратора инстанс рабочего пользователя не сможет защитить трафик остальных.

Это жертва частью изоляции ради сетевой безопасности. Утечка хуже.

---

## Зачем Proxifier с перехватом чужих пользователей и служб

**Контекст:** на одном Windows Server могут одновременно работать несколько RDP-сессий. Proxifier — single-instance приложение: одна GUI-копия на весь компьютер.

**С настройками по умолчанию:**

- Proxifier ловит трафик только того пользователя, под которым запущен
- Кто первым залогинился — тот защищён, второй идёт мимо прокси
- **Тихая утечка IP для второго пользователя** — её не видно, пока не проверишь специально

**С включёнными «Applications run by other users» и «Windows services and other system processes»:**

- Чей Proxifier запущен — тот ловит трафик всех пользователей и системных служб
- Первый залогинившийся защищает обоих
- Второй автозапуск даёт попап «уже запущено», но трафик идёт через прокси

### Зачем DNS and IP Leak Prevention Mode

Если Proxifier не может достучаться до прокси — сетевая проблема, прокси упал — он **блокирует** трафик вместо того, чтобы пустить его напрямую.

Это kill switch. Обратная сторона: лёг прокси — встала вся машина. Это осознанный размен: лучше остановка, чем тихая утечка.

### Почему именно статический резидентский прокси

- **Статический, а не ротационный** — ротация меняет IP каждые минуты, что ломает любые залогиненные сессии: бесконечные подтверждения, разлогины, 2FA на каждый чих. Для машины, которая должна работать ночью без тебя, это убийственно.
- **Резидентский, а не VPN** — коммерческие VPN дают датацентровые IP из общих пулов. Зашарены на тысячи людей, половина в чёрных списках, капчи там, где их быть не должно.
- **Dedicated** — IP только твой.

## Зачем лицензия Proxifier на всех пользователей

По умолчанию лицензия пишется в пользовательскую ветку реестра. На многопользовательском сервере это значит, что каждый новый пользователь видит триал, пока сам не активирует.

Галка **«for all users of this computer»** при активации переносит лицензию в машинную ветку — её видят все, включая пользователей, созданных потом.

Лицензия per-machine: Standard покрывает две машины, на каждой активируется отдельно.

## Почему режим `auto`, а не `bypassPermissions`

**Что хотелось:** чтобы Claude Code не спрашивал разрешение на каждую правку файла.

**Что случилось:** `bypassPermissions` в десктопной версии спонтанно откатывается на более строгий режим сразу после первого сообщения. Это известные issue в трекере Anthropic, помеченные **«not planned»** — чинить не будут.

**Что выбрали:** режим `auto`. Чуть консервативнее — иногда спрашивает на чувствительной операции — но не сбрасывается.

**Альтернатива, которую рассматривали:** CLI с флагом пропуска разрешений работает железно, но требует ходить через терминал вместо десктопного GUI. Тот же компромисс, что и в вопросе Windows против Linux, просто с другой стороны.

---

## Почему Scoop, а не обычные установщики

- Per-user установка, не требует прав администратора на обновления
- Не лезет в `Program Files` и системные пути
- Node, mise, 7zip — одной командой
- Сносится одной командой

Альтернативы: установщик Node лезет в `Program Files` и требует админа на апгрейд; nvm-windows управляет только Node, а не всем тулингом.

---

## Почему mise, а Node не ставится глобально

Node и pnpm приезжают **per-project** через `.tool-versions` в репозитории.

- Два проекта на разных версиях Node живут рядом и не конфликтуют
- Новый человек получает ровно ту версию, на которой проект собирали
- Версия зафиксирована в git, а не в голове

**Глобальный Node рядом с mise — это ошибка**, и я её когда-то допустил. Два источника Node в PATH дают ровно тот класс проблем, который потом ищешь полдня: команда есть, но версия не та; или `pnpm` виден в одном шелле и не виден в другом.

### Почему shims, а не `mise activate`

На Windows `eval "$(mise activate bash)"` возвращает PATH с разделителями `;` вместо `:`, после чего Git Bash перестаёт находить вообще всё — `git`, `ls`, `which`. Выглядит как «сломалась система».

Поэтому в `.bashrc` только добавление каталога shims в PATH руками.

Побочный эффект: `mise doctor` показывает `shims_on_path: no`. Это **не ошибка** — у mise два режима активации, и в shims-режиме этот пункт всегда `no`.

## Почему рецепты написаны для Claude, а не как bash-скрипты

Каждый рецепт в этом репозитории адресован одновременно человеку и Claude Code: в шапке сказано, что от него ожидается, дальше идёт обычный markdown с командами.

**Скрипт падает на первом отличии машины, Claude адаптируется.** На одной машине Scoop уже стоял, на другой PowerShell запрещает исполнение скриптов, на третьей версия Windows Server такая, что нужного пункта в настройках просто нет. Скрипт в каждом случае либо падает, либо — хуже — проходит мимо и делает вид, что всё хорошо.

**Инструкция остаётся читаемой.** Это тот же файл, который открываешь сам, когда хочешь вспомнить, что происходит на шаге 4. Скрипт нельзя прочитать как документацию, документацию нельзя выполнить.

**Грабли живут рядом с шагами.** Claude сам заглядывает в `TROUBLESHOOTING.md`, когда упирается.

### Поэтому же — блоки проверки

Claude может отчитаться об успехе там, где успеха не было: команда вернула пустой вывод, он счёл это нормой.

Каждый слой кончается блоком из нескольких команд с ожидаемым выводом, который **прогоняет человек**. Это тридцать секунд, отделяющие «вроде поставилось» от «поставилось».

## Почему секретов нет в репозитории

Соблазн положить рядом SSH-ключ, профиль прокси и OAuth-токены велик: тогда новая машина поднимается одним клоном.

Минусы перевешивают:

- Если репозиторий случайно станет публичным — катастрофа, причём отложенная: история git сохранит секреты даже после удаления файла
- Ключ в репозитории живёт вечно и ротируется только вручную
- Любой, кому дашь клон-ссылку «посмотреть», получит доступ ко всему

Поэтому здесь: `config.json` в `.gitignore`, пароль спрашивается в момент выполнения и нигде не сохраняется, профиль Proxifier экспортируешь сам.

Если делаешь свой форк с секретами внутри — делай его приватным и помни про историю git.

## Что рассматривали и не стали делать

### Proxifier Service Edition

Запускает Proxifier как системную службу — самое чистое решение для многопользовательской машины.

Не взяли: дороже, а перехват чужих пользователей в Standard работает достаточно хорошо для режима «наполовину один». Если у тебя реально два активных человека каждый день — это правильная покупка.

### Запуск Proxifier службой через сторонние обёртки

Технически возможно и без Service Edition. Но GUI в системной сессии не показывает иконку в трее — теряется возможность глазами проверить, что всё работает. Нестабильное обходное решение.

### Резервный прокси

Автоматическое переключение на запасной IP ломает всё, ради чего схема затевалась — единый стабильный исходящий адрес. Лучше остановка работы, чем незаметная смена IP.
