## §0. Настройка np (один раз на машину)

Скрипт [`np.sh`](np.sh) ставится в слое 1. Настраивается переменными окружения в `~/.bashrc`:

```bash
export NP_OWNER="your-github-login"          # по умолчанию берётся из gh auth
export NP_TEMPLATE="your-org/your-template"  # нужен только для сценария A
export NP_PROJECTS="$HOME/projects"          # по умолчанию ~/projects
```

`NP_TEMPLATE` — твой собственный репозиторий-шаблон на GitHub (с галкой Template repository в настройках). Если шаблона нет, сценарий A просто не работает, остальные два — работают.

## §1. Что спросить у юзера

Спроси одним ходом:

| Сценарий | Когда | Что нужно |
|---|---|---|
| **A. Новый из шаблона** | Новый проект, репозитория ещё нет | имя в kebab-case, напр. `clinic-landing` |
| **B. Клон своего** | Репозиторий уже на твоём GitHub | имя (= имя репо) |
| **C. Чужой репозиторий** | Тебя позвали коллаборатором | полное `<owner>/<repo>` |

Опционально: нужен ли `--no-deps` (только клон, без зависимостей).

## §2. Выполнить через np

### A. Новый из шаблона

```bash
np new <site>
```

Создаст приватный репозиторий из `$NP_TEMPLATE`, склонирует, поставит toolchain и зависимости.

### B. Клон своего

```bash
np clone <site>
```

⚠️ При **первом** клоне с этой машины `gh` попросит подтвердить SSH fingerprint github.com — ответить `yes`. Разовая операция.

**После клона напомни, что не приезжает с git:**

- **`.env.production`** — он в `.gitignore`. Для локальной разработки обычно можно работать и без него. Забрать со старой машины или с прода.
- **SSH-доступ к боевому серверу** — публичный ключ этой машины (`~/.ssh/id_ed25519.pub`) надо добавить в `authorized_keys` деплой-пользователя.

### C. Чужой репозиторий

```bash
np collab <owner>/<repo>
```

Перед клоном проверит, что приглашение принято.

**Напомни про ограничения режима коллаборатора:**

- Прямой push в основную ветку обычно закрыт защитой → работа через ветки и pull request
- Доступа к секретам окружения нет
- Доступа к `.env.production` владельца нет
- Новый секрет добавляет владелец у себя в настройках репозитория; приедет при следующем мерже

### Опции

```bash
np new site --owner some-org    # другой владелец
np clone site --no-deps         # только клон
```

## §3. Ручной путь (если np не стоит)

Те же шаги шестью командами:

```bash
cd ~/projects

# A — новый из шаблона:
gh repo create <owner>/<site> --template <owner>/<template> --private --clone
# B — клон своего:
gh repo clone <owner>/<site>
# C — чужой:
gh repo clone <owner>/<repo>

cd <site>
mise install
pnpm install          # если есть package.json
pnpm approve-builds   # в меню: a → Enter → y → Enter
```

> ⚠️ **`gh repo create --clone` клонирует в текущую папку.** Обязательно `cd ~/projects` **перед** командой, иначе репозиторий ляжет вложенно.

> ⚠️ Если `package.json` нет — `pnpm install` упадёт с `ERR_PNPM_NO_PKG_MANIFEST`. Это нормально для пустого шаблона, см. §5.

```

Дальше:
```

Важно открывать проект **новой сессией** Claude Code, а не продолжать текущую: так у него будет чистый контекст именно этого проекта.

## §5. Проект без package.json

После клона `ls package.json` ничего не выводит — значит это пустой шаблон, который ещё не инициализирован.

**Не пытайся ставить зависимости.** `np` сам это заметит и пропустит шаг с предупреждением.

Скажи юзеру: открой проект новой сессией Claude Code и попроси инициализировать. После этого `package.json` появится, и зависимости поставятся обычным путём.

## §6. Про порты

Когда на машине несколько проектов, два параллельных дев-сервера начинают играть в чехарду: 3000 занят — беру 3001. Через неделю уже не помнишь, кто где.

Пропиши каждому проекту свой порт в `package.json` сразу:

```json
"dev": "next dev -p 3000"   // проект 1
"dev": "next dev -p 4000"   // проект 2
```
